# المرحلة الرابعة — تدقيق أمان التطبيق

**الحالة الحالية:** تتضمن مراجعة المرحلة الرابعة على الفرع `main` إصلاحات PR #227 وPR #228 وPR #230، وتوثيق جرد ACL التكراري لمساحة العمل في PR #232، ومراجعة أمان النقل في PR #233. لا تُعد هذه المراجعة شهادة أمن شاملة أو اعتمادًا نهائيًا للإصدار.

## نطاق المراجعة

تم فحص مسارات تنفيذ أدوات الوكيل، موافقات المستخدم المحلية، أوامر البرامج و.NET، القراءة والكتابة داخل مساحة العمل، التحكم في Edge عبر CDP، اتصالات REST، عميل مزود الذكاء الاصطناعي، تخزين DPAPI، وتكامل Gmail للقراءة فقط.

هذه مراجعة كود مركزة وليست اختبار اختراق شاملًا أو شهادة أمان للنظام المثبت. أُجري جرد ACL تكراري للقراءة فقط لعناصر مساحة العمل المعتمدة بتاريخ 2026-11-24؛ ولا يشمل ذلك أي مسار خارج جذر المستودع أو اختبارات Windows العملية.

## النتائج والإجراءات

### 1. متوسط — تحويلات HTTP في تدفق Gmail OAuth

كان عميل Gmail الافتراضي يستخدم `HttpClient` بإعداد التحويل التلقائي الافتراضي. طلب تبادل رمز التفويض يرسل `code` وPKCE verifier في جسم POST، وطلب تجديد الوصول يرسل refresh token. تحويل HTTP من نوع 307/308 يمكن أن يعيد إرسال جسم POST إلى وجهة التحويل.

**المعالجة — مدمجة في PR #227:** إنشاء `HttpClientHandler` صريح مع `AllowAutoRedirect=false` وبدون cookies أو Windows default credentials. أصبحت استجابة التحويل غير الناجحة تُرفض بدل اتباعها.

### 2. منخفض — تحويلات HTTP من نقطة Edge DevTools المحلية

عميل اكتشاف CDP كان يتصل بعناوين loopback المشتقة من `DevToolsActivePort` باستخدام عميل HTTP يسمح افتراضيًا باتباع التحويلات. لو أشارت نقطة محلية غير موثوقة إلى استجابة redirect، فقد يتبعها العميل إلى وجهة أخرى بدل البقاء على loopback.

**المعالجة — مدمجة في PR #227:** تعطيل التحويلات والـ cookies وWindows default credentials في عميل اكتشاف CDP. يظل التحقق من عنوان WebSocket والمنفذ والمسار loopback قائمًا في `BrowserCdpTransport`.

### 3. منخفض — تصنيف غير مكتمل لبعض آثار الأدوات في سجل الموافقات

تصنيف `browser_navigate` و`web_search` لم يكن يضع Execute، رغم تنفيذ اتصال شبكي. كما أن `click_ui_control` و`fill_ui_text` لم يظهرا احتمال المشاركة الخارجية في التصنيف، مع أن التطبيق الخارجي قد يرسل تغييرات أو نصًا تلقائيًا.

**المعالجة — مدمجة في PR #227:** تحديث التصنيف ليعكس Execute وModify وExternalShare حسب نوع الفعل. هذا تعديل لتوصيف سجل التدقيق؛ لا يغيّر آلية الموافقة نفسها.

### 4. متوسط — سباق فصل Gmail مع تجديد الرمز

كان تجديد رمز الوصول يستطيع حفظ Refresh Token دوّار بعد أن يضغط المستخدم Disconnect، لأن تحديث الرمز وحذف بيانات الاعتماد لم يكونا متزامنين. كما أن نافذة Gmail كانت تسمح بالفصل أثناء قراءة الرسالة لأن القراءة تستخدم CancellationTokenSource منفصلًا عن عملية تحديث القائمة.

**المعالجة — مدمجة في PR #228:** إضافة جيل اعتماد متزايد مع قفل قصير حول قراءة/حفظ/حذف الاعتماد وتحديث cache. أي تجديد أو OAuth callback بدأ قبل الفصل/إعادة الربط يُرفض إذا عاد بعد تغيّر الجيل، ولا يستطيع إعادة إنشاء الرمز. كذلك يتم إلغاء قراءة الرسالة النشطة قبل حذف الرمز المحلي.

### 5. منخفض — رسائل الاستثناء في سجل الأعطال المحلي

كان تعليق `WriteCrashLog` يذكر أن سجل الأعطال يحفظ نوع الاستثناء والـ stack trace فقط، لكن التنفيذ كان يضيف `exception.Message` أيضًا. نص رسالة الاستثناء ليس مضمونًا أن يكون خاليًا من بيانات أدخلها المستخدم؛ فقد يتضمن مسارًا محليًا أو عنوانًا أو جزءًا من قيمة حساسة بحسب مصدر الخطأ.

**المعالجة — مدمجة في PR #230:** حذف رسالة الاستثناء من السجل المحلي مع الاحتفاظ بالطابع الزمني ومصدر الحدث ونوع الاستثناء والـ stack trace. لا يغيّر ذلك رسالة الخطأ التي تظهر للمستخدم في واجهة التطبيق؛ التغيير يخص ما يُحفظ على القرص فقط.

### 6. متوسط — إرسال بيانات API بعيدة عبر HTTP غير مشفر

كان التحقق من Base URL يقبل HTTP لأي مضيف. التحذير كان يظهر في شاشة موافقة استدعاء الوكيل عند استخدام المصادقة، لكنه لم يمنع مسار اختبار الاتصال اليدوي من إرسال Bearer أو Custom Header عبر HTTP، كما لم يمنع إرسال أجسام طلبات غير مشفرة إلى مضيف بعيد.

**المعالجة — في PR #233:** يرفض بناء URI الخاص بالطلب أي HTTP غير Loopback قبل الإرسال، بما يشمل الاختبار اليدوي والاستدعاءات المعتمدة والإرسال المباشر، حتى عند عدم وجود بيانات اعتماد. يبقى HTTP متاحًا لخدمة Loopback على الجهاز نفسه فقط. تُعطّل التحويلات التلقائية وCookies وبيانات اعتماد Windows الافتراضية في عميل API الافتراضي. قد تظل ملفات الاتصال البعيدة القديمة محفوظة، لكن يلزم تحديث عنوانها إلى HTTPS قبل استخدامها.

### 7. منخفض — التحويلات التلقائية في طلبات الطقس

كان WeatherService يستخدم عميل HTTP افتراضيًا يتبع التحويلات تلقائيًا رغم أن نقاط النهاية ثابتة وتبدأ بـHTTPS. طلب الطقس قد يحتوي على اسم مدينة أو إحداثيات دقيقة؛ لذلك لا ينبغي إعادة توجيهه تلقائيًا إلى مضيف آخر أو إلى HTTP.

**المعالجة — في PR #233:** يستخدم WeatherService معالجًا يرفض التحويلات ويعطّل Cookies وبيانات اعتماد Windows الافتراضية. تظهر استجابة 3xx كفشل بدل متابعة الوجهة الجديدة.

### 8. منخفض — عزل Cookies في تنزيل الموارد ومخزن Ollama Registry

كانت بعض العملاء تتبع التحويلات يدويًا وتتحقق من كل وجهة، لكنها تركت CookieContainer الافتراضي مفعّلًا رغم عدم حاجتها إلى Cookies. قد يؤدي ذلك إلى استمرار Cookies بين طلبات المضيف نفسه؛ كما قد تتشارك خدمة تنزيل الموارد حالة Cookies بين المضيفين المسموح بهم.

**المعالجة — في PR #233:** تعطيل تخزين Cookies في عملاء تنزيل الموارد وOllama Registry، مع الإبقاء على التحقق الحالي من مضيف التحويلات وقصرها على HTTPS.

## الضوابط التي ظهرت موجودة في الكود

- أدوات الوكيل مسجلة بقائمة محددة، والتنفيذ يمر عبر dispatch صريح؛ الاسم غير المعروف يُرفض.
- تشغيل البرامج يستخدم قائمة ثابتة ومسارات Windows موثوقة، وليس أمر shell حرًا.
- أوامر build/test مقيدة بمشروع داخل مساحة العمل، وتتطلب موافقة، وتستخدم مسار dotnet محددًا، مع فحص hash ومهلة زمنية وقتل شجرة العملية عند انتهاء المهلة.
- عمليات الملفات تقيّد المسارات داخل مساحة العمل، وترفض reparse points، وتستخدم حدود أحجام وموافقات وكتابة ذرية/نسخ احتياطية.
- التحكم في المتصفح يستخدم ملف Edge منفصلًا، ويشترط صفحة واحدة غير ملتبسة؛ القراءة والملاحة والتفاعل والرفع والتنزيل لها موافقات مستقلة.
- اتصالات API تتطلب موافقة على الطلب المحدد، وتربط الموافقة ببصمة إعداد الاتصال، وتحد من حجم الاستجابة. تُرفض الطلبات البعيدة عبر HTTP قبل الإرسال، ولا تُتبع التحويلات، ولا تُستخدم Cookies أو بيانات اعتماد Windows الافتراضية.
- اتصالات API وبيانات Gmail والسجلات المحفوظة تستخدم DPAPI للمستخدم الحالي عبر مخازن JSON المحمية. بعض الأسرار المنفردة تستخدم `DpapiSecretStore` مباشرة؛ يجب تدقيق كل مسارات التحديث والاسترداد الخاصة بها على حدة.
- تكامل Gmail يستخدم OAuth مع PKCE ونطاق `gmail.readonly`، وعمليات صندوق البريد قراءة فقط.

- أظهر الجرد التكراري للقراءة فقط `65,547` عنصرًا تم تعدادها، و`23` عنصرًا له قواعد صريحة أو وراثة محمية تستحق الفحص التفصيلي، و`0` أخطاء، و`0` نقاط Reparse مستبعدة.

- في مجلدي `Layal\SpeechEvaluation` اللذين ظهرا في النتائج: الوراثة محمية (`AreAccessRulesProtected = True`). القواعد الصريحة الظاهرة هي `FullControl / Allow` لكل من `OWNER RIGHTS` و`NT AUTHORITY\SYSTEM` و`BUILTIN\Administrators`. المالك المسجل هو حساب المستخدم الحالي؛ و`OWNER RIGHTS` هو SID خاص بصاحب العنصر، وليس مجموعة مستخدمين عامة.
- في عناصر `artifacts\windows-live-acceptance` التسعة عشر: المالك هو حساب المستخدم الحالي، والقواعد المعروضة تقتصر على `MELHEGAZ\Mohamed.Fathy` و`BUILTIN\Administrators` و`NT AUTHORITY\SYSTEM` بصلاحية `FullControl / Allow`. ظهرت في بعض العناصر قواعد صريحة تكرر قواعد موروثة مماثلة؛ وهو تكرار في ACL لا يثبت بحد ذاته وجود وصول إضافي.
- لم تظهر قواعد `Deny` أو هويات عامة مثل `Everyone` أو `Users` أو حسابات غير متوقعة في القواعد الكاملة للعناصر الـ23 المفحوصة تفصيليًا. العناصر الأخرى التي لم تُدرج ضمن النتائج لم يكن لديها قواعد صريحة أو وراثة محمية وفق شرط الاكتشاف المستخدم، ولذلك تعتمد على وراثة ACL من المسار الأب.
- لم يجرِ أي تعديل على ACL أو على ملفات بيانات المستخدم نتيجة هذه المراجعة.

**التقييم:** لا تشير النتائج الحالية إلى حاجة لتعديل صلاحيات NTFS داخل مساحة العمل المعتمدة. تُترك قواعد الملفات المحلية وملفات DPAPI كما هي؛ ولا تُجرى إزالة للقواعد المكررة دون مبرر واختبار منفصل. يظل هذا الاستنتاج خاصًا بمساحة عمل المستودع، ولا يقيّم مسارات بيانات التطبيق خارجها.

## اختبارات أضيفت في هذه المراجعة

- اختبار حتمي يحجز استجابة تجديد OAuth، ينفذ Disconnect، ثم يعيد استجابة متأخرة تحتوي Refresh Token دوّارًا؛ ويتحقق أن الرمز لا يعود وأن أي طلب Gmail لا يُرسل بعدها.
- تأكيد أن عميل Gmail الافتراضي يرفض التحويلات ولا يستخدم cookies أو Windows default credentials.
- تأكيد أن عميل اكتشاف Edge DevTools المحلي يرفض التحويلات ولا يستخدم cookies أو Windows default credentials.
- تأكيد أن سجل الموافقات يصنف الملاحة والبحث والتفاعل مع تطبيقات خارجية بما يعكس آثار التنفيذ والتعديل والمشاركة الخارجية.
- اختبار أن سجل الأعطال لا يكتب نص رسالة الاستثناء، حتى عندما تحتوي على علامة نصية حساسة، مع الاحتفاظ بنوع الاستثناء ومصدر الحدث.

## حالة التحقق بعد دمج PR #228

اكتملت فحوص ما بعد الدمج على commit `4880df73dfe4ccf917269e24fc9c4afe6b9bb1c9` بنجاح، بما في ذلك:
- بناء Windows وتشغيل الاختبارات الآلية وتكاملات النقر والسحب ولوحة المفاتيح وDPI/الشاشات ومعاينة GLB.
- فحوص Gitleaks وNuGet audit وCodeQL.
- بناء توزيع CI غير موقّع واختبار دورة حياة المثبّت: تثبيت جديد، ترقية، rollback، وإزالة.
- إنشاء ورفع ملفات التوزيع وتقارير الاختبارات وملف SBOM وSHA-256 manifest.

**القيود:** تم تخطي التوقيع الرسمي وقبول Windows اليدوي في CI كما هو متوقع لعدم توفر شهادة توقيع معتمدة ودليل قبول يدوي. نجاح CI لا يعني أن الحزمة موقعة أو أن القبول البشري النهائي اكتمل.

## حدود لم تُحسم في هذه الجولة

- لم يُجرَ اختبار اختراق ديناميكي شامل على نسخة Windows مثبتة أو على حسابات/خدمات فعلية.
- اكتمل جرد ACL للقراءة فقط لعناصر مساحة العمل التي أمكن تعدادها: 65,547 عنصرًا، دون أخطاء أو Reparse points مستبعدة؛ لم تظهر في العناصر الـ23 ذات القواعد الصريحة/المحمية هويات عامة أو قواعد Deny. لا يشمل ذلك أي بيانات تطبيق خارج جذر المستودع.
- لم تُراجع إعدادات Windows Defender/SmartScreen أو فعالية الحماية من حساب Windows آخر.
- يمنع موصل API العام إرسال أي طلب إلى مضيف غير Loopback عبر HTTP، ويفرض عميل مزود الذكاء الاصطناعي HTTPS على الخدمات البعيدة. يظل تقييم سياسة الصلاحيات وجودة حماية البيانات داخل كل خدمة خارجية ومسؤولية مالكها خارج نطاق التحقق المحلي؛ ولا يحل نجاح اختبار النقل محل مراجعة صلاحيات API لكل مزود.
- لا تزال مراجعة مصادر الأصول والتبعيات والتراخيص، إعداد شهادة توقيع موثوقة، وقبول الواجهة اليدوي ومتعدد الشاشات خارج نطاق هذا التغيير.

**معيار الإغلاق:** لا تُعتبر المرحلة الرابعة مكتملة بمجرد دمج إصلاحات PR #227 وPR #228 أو نجاح CI؛ يلزم استكمال مراجعة دورة حياة الجلسات والأسرار، حسم ACL مجلد بيانات التطبيق، اختبارات Windows العملية، ومعالجة أي نتائج إضافية تظهر في مراجعة بقية الخدمات.
