# دليل اتساق التصميم والحالات المرئية — ليال

**نطاق الدليل:** الواجهة الأساسية والشخصية العائمة، العربية/الإنجليزية، الثيمات، وإشعارات الحالة. هذا الدليل يعرّف معيار مراجعة التصميم ولا يثبت القبول اليدوي على جهاز معين.

## 1. قواعد الألوان

- في الوضع العادي تستخدم الواجهة موارد `Layal.Color.*` و`Layal.*` المشتركة بدل ألوان محلية جديدة داخل الأقسام.
- في Windows High Contrast تكون ألوان النظام هي المصدر المرجعي للنص والخلفية والحدود والتركيز؛ تتوقف التدرجات والظلال الزخرفية في السطح الرئيسي، ويظهر للشخصية حد صريح ويختفي التوهج والجسيمات الزخرفية.
- الحالة لا تُعبّر عنها باللون وحده: يجب أن يحمل النص وصفًا مفهومًا مثل نجاح أو تحذير أو فشل/إلغاء، وأن تبقى الرسالة قابلة للقراءة في تباين Windows.
- استخدم `Layal.Success` و`Layal.Warning` و`Layal.Danger` للحالات الدلالية، و`Layal.Muted` للمعلومات المساندة فقط. لا تستخدم اللون الخافت لرسالة خطأ تتطلب تصرفًا.

## 2. اتجاه النص

- يظل جذر النافذة وتخطيط الأيقونات LTR لتجنب عكس رموز التنقل أو الأشكال الرسومية.
- تُحاذى النصوص العربية إلى اليمين محليًا، والنصوص اللاتينية/الروابط/معرّفات النماذج إلى اليسار.
- قوائم سجل المهام والمهارات والذاكرة والمهام السابقة ورسائل المحادثة تستخدم اتجاه النص حسب المحتوى أو الاتجاه الذي تم تحديده للمحادثة.
- يجب اختبار النسخ إلى الحافظة؛ لا ينبغي نسخ علامات Unicode غير المرئية للعزل الاتجاهي إذا لم تكن جزءًا من النص الأصلي.

## 3. الحالات الفارغة

تستخدم حالة القائمة الفارغة قالب `Layal.EmptyStateText`: نص مساند واضح، متعدد الأسطر، بعرض أقصى يمنع السطر الطويل جدًا، ولا يتلقى النقرات بدل عنصر التحكم تحته. هذه الحالات مترجمة ومسماة عبر UI Automation:

| القسم | عندما تكون القائمة فارغة | ما الذي ينهي الحالة؟ |
|---|---|---|
| المحادثة | توجيه المستخدم لكتابة رسالة وبدء المحادثة | ظهور رسالة واحدة على الأقل |
| سجل أحداث المهمة | إرشاد المستخدم لبدء مهمة | ظهور حدث مهمة |
| المهام السابقة | توضيح عدم وجود سجل سابق | حفظ مهمة سابقة |
| المهارات | إرشاد المستخدم لاستيراد ZIP أو GitHub | تثبيت مهارة |
| الذاكرة | إرشاد المستخدم لإنشاء ملاحظة | حفظ ملاحظة |

لا تعرض حالة فارغة فوق بيانات موجودة، ولا تُخفِ عناصر التحكم أو تمنع وصول لوحة المفاتيح إلى القائمة الأصلية.

## 4. الحالة والإعلان لقارئ الشاشة

- حالة النشاط لا تُخلط بحالة اتصال المزود؛ لكل منهما عنصر واجهة واسم UI Automation مستقل.
- الرسائل التي تتغير نتيجة إرسال/إيقاف/فشل المحادثة، وتغيّر اتصال المزود، ونتائج الإجراءات والمهام، مهيأة كـ live regions غير مقاطعة `Polite`، ويُرفع حدث `LiveRegionChanged` عند التحديث عبر مساعد مركزي.
- لا ترفع إعلانًا مكررًا إذا لم يتغير النص، ولا تعلن منطقة حالة فارغة كما لو كانت هناك نتيجة.
- يجب أن يحتوي نص الخطأ على الإجراء أو السبب المتاح للمستخدم، وأن يعكس الفشل أو التحذير بصدق. لا يجوز تحويل رفض الموافقة أو فشل أداة إلى حالة نجاح.

## 5. معيار مراجعة العرض

كرر الفحص لكل من العربية والإنجليزية، ولكل من الثيم الفاتح والداكن، مع Windows High Contrast:

1. لا يحدث قص أو تداخل للنصوص والحقول والقوائم ورسائل الخطأ.
2. يظهر التركيز المرئي عند استخدام لوحة المفاتيح فقط، ولا يختفي بين الأقسام.
3. النصوص المختلطة، وخصوصًا URL ومعرّف النموذج ومفتاح المزود، تقرأ وتنسخ في الترتيب الصحيح.
4. تظل رسائل الحالات الفارغة والأخطاء والنتائج مقروءة ومعلنة باسم مفهوم.
5. لا تعتمد الرسالة على اللون وحده، ولا تتسبب الحركة الزخرفية في إخفاء الحالة.
6. عند المقاييس المتاحة 100/125/150/175% لا يحدث قص؛ يجرى اختبار منفصل بنقل الشخصية بين شاشتين بمقياسي DPI مختلفين.

## 6. حدود اعتماد الاختبار

- الاختبارات الآلية تختبر موارد الألوان، أسماء الحالات، اتجاه/محاذاة النص، وتمثيل الواجهة في WPF.
- لقطات العرض التي تغيّر `renderScale` لا تغيّر إعداد Display Scale الحقيقي في Windows.
- لا يُعتمد دعم قارئ الشاشة أو High Contrast أو انتقال DPI متعدد الشاشات إلا بعد تجربة تفاعلية موثقة على نسخة Release المرشحة نفسها.
- يسجل كل بند بإحدى الحالات `PASS` أو `FAIL` أو `BLOCKED` أو `NOT TESTED`، مع commit ودليل، في [سجل القبول الحي](WINDOWS_LIVE_ACCEPTANCE_REPORT_AR.md) و[سجل إتاحة الوصول](ACCESSIBILITY_KEYBOARD_ACCEPTANCE_AR.md).
