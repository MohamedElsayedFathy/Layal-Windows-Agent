**النطاق:** جرد هيكل المستودع، توزيع الطبقات والوظائف، مواضع التكدس، الاختبارات وبوابات الجودة، وخطة تنظيم مرحلية.

## 1. ملخص هندسي

المشروع تطبيق Windows WPF على .NET 10، ويجمع حاليًا واجهة العرض والمنطق التطبيقي وخدمات Windows والتكاملات في مشروع إنتاجي واحد هو `Layal.Desktop`. مشروع الاختبارات الوحيد `Layal.Tests` يشير مباشرة إلى مشروع سطح المكتب.

المشكلة الأساسية ليست نقص الملفات أو غياب الاختبارات؛ بل اتساع بعض وحدات الكود، واعتماد واجهة العرض على حالة تطبيق عامة mutable، ووجود خدمات كبيرة تجمع أكثر من مجال تنفيذي. لذلك يجب أن يكون التنظيم قائمًا على **حدود المسؤوليات والاعتماديات**، وليس على إعادة تسمية الملفات فقط.

## 4. حدود الطبقات الحالية

### واجهة العرض
`MainWindow` يحتوي على عدد كبير من event handlers وحالات UI وعمليات تنسيق/تخزين/تشغيل. يوجد فصل مبدئي إلى Views وServices، لكنه ليس فصلًا حقيقيًا بين Presentation وApplication لأن code-behind يستدعي الخدمات ويقرأ `AppRuntime` مباشرة.

### تركيب الخدمات وحالة التطبيق
`AppRuntime` هو Service Locator عام بخواص static قابلة للتغيير، وكثير منها يبدأ بقيمة `null!`. `App.OnStartup` ينشئ الخدمات ويملأ تلك الخواص ثم تنشئ الواجهات بعض الخدمات بنفسها. هذا يجعل ترتيب الإنشاء والإغلاق والاعتماديات الضمنية ومسارات الاختبار أكثر تعقيدًا من اللازم.

### تنفيذ أدوات الوكيل
`AgentToolExecutor` نقطة دخول مفيدة ومحددة للأدوات، لكن تنفيذ أدوات ملفات ومسارات Windows والبحث/المتصفح والبناء والذاكرة متداخل في class واحد. المطلوب الحفاظ على نقطة التوجيه مع فصل منفذي الأدوات إلى وحدات داخلية مستقلة، والإبقاء على `PermissionBroker` شرطًا قبل أي أثر جانبي.

### المتصفح وواجهات Windows
`BrowserAutomationService` يجمع سياسات التحقق وإدارة جلسة Edge وCDP وقراءة الصفحة وتنفيذ الأفعال. `WindowsUiAutomationService` يطبق مجالًا مستقلًا هو UI Automation. ينبغي فصل السياسات عن transport/session وعن use cases، مع عدم إضعاف التحقق من الوجهة أو المعاينة والموافقة وإثبات النتيجة.

### النماذج والاختبارات
الأنواع والـ policies موزعة حاليًا داخل مشروع Desktop، والاختبارات تشير إليه مباشرة. الفصل إلى Core/Application/Infrastructure يتطلب أولًا تعريف عقود مستقرة وإزالة اعتماد الواجهات على الـ static state؛ نقل الملفات دفعة واحدة سيخلق اعتماديات دائرية أو يكسر اختبارات WPF.

## 5. التغييرات المنفذة في حزمة التنظيم الأولى

تم اختيار تقسيم `MainWindow.xaml.cs` إلى partial class files حسب مجال الوظيفة، مع إبقاء:
- نفس class والـ namespace والحقول والـ constructor.
- نفس أسماء event handlers وتواقيع الدوال وأجسامها وترتيبها.
- نفس عناصر XAML وعمليات الربط.
- عدم تغيير أي قرار أمني أو permission أو side effect.

تم تحديث `tools/validate_project.py` ليجمع كل ملفات `MainWindow*.cs` بدل قراءة الملف الأصلي فقط؛ وبالتالي تظل فحوصات ربط الوظائف والسلوك موجودة بعد التقسيم.

هذه **إعادة تنظيم بنيوية فقط** وليست ادعاءً بأن منطق الواجهة أصبح ViewModels أو أن الاعتماديات قد فُصلت.

## 6. الخطة المرحلية التالية

1. **إكمال تقسيم واجهة MainWindow**: مراجعة كل partial مقابل المجال الذي يحتويه، ومطابقة كل حدث XAML مع handler، وتشغيل static checks وWindows build والاختبارات.
2. **تخفيف code-behind**: استخراج ViewModels/Presentation controllers على دفعات صغيرة حسب الشاشة: Chat، Tasks، Memory، Settings/Integrations، Voice/Camera. لا يتم نقل منطق قبل تحديد lifecycle وthreading وcancellation.
3. **تقسيم AgentToolExecutor**: الإبقاء على router/registry، ونقل التنفيذ إلى WorkspaceFileTools وWindowsAutomationTools وSearchBrowserTools وBuildTools وMemoryTools. فرض PermissionBroker مركزيًا عند حدود التنفيذ، مع target binding والتحقق قبل وبعد الأفعال.
4. **تقسيم BrowserAutomationService**: BrowserUrlPolicy وEdgeSession/CDP transport وPageReadService وBrowserActionService؛ مع اختبارات SSRF/redirect/DNS rebinding/selector/action/upload.
5. **تأسيس Composition Root**: استبدال `AppRuntime` تدريجيًا بكائن خدمات typed immutable يُنشأ مرة في startup ويمرر للواجهات. التخلص من global mutable state فقط بعد تحديث اختبارات الـ startup/shutdown.
6. **تنظيم الموارد المرئية**: استخراج ResourceDictionaries للـ typography/tokens/controls/themes من `App.xaml`، ثم تقسيم واجهات XAML الكبيرة إلى UserControls حسب الشاشة.
7. **فصل طبقات المشاريع**: بعد استقرار العقود، إنشاء Domain/Core وApplication وInfrastructure.Windows وإبقاء WPF داخل Desktop. لا يُنقل أي نوع قبل إثبات أنه لا يعتمد على WPF/Windows أو على طبقة أعلى.
8. **تنظيم أدوات المطور والتوثيق**: تقسيم `tools` حسب Validation/Acceptance/Release/Asset tooling، وتجميع الوثائق حسب Architecture/Operations/Acceptance/Release مع الإبقاء على مصدر واحد معتمد لكل حالة.
9. **تثبيت معايير الجودة**: حدود أحجام للملفات الجديدة، analyzers/formatting، عدم وجود dead code، واختبارات unit/integration/manual واضحة لكل capability.

## 7. قواعد عدم كسر السلوك

- لا نحذف وظيفة أو control أو tool لمجرد أنها غير مستخدمة ظاهريًا؛ نتحقق من XAML/event wiring والـ reflection والاختبارات أولًا.
- لا نغير أسماء إعدادات المستخدم أو مسارات DPAPI/الملفات أو تنسيقات التخزين في حزمة إعادة التنظيم.
- لا نبدل سياسات الموافقة أو حدود workspace أو صلاحيات المتصفح أو الخصوصية أثناء نقل الكود.
- لا ندمج إلى `main` دون Windows build والفحوصات الآلية ذات الصلة، ثم مراجعة التغيير وسجلات القبول العملية المناسبة.
- الاختبار الأخضر لا يثبت وحده اكتمال القبول اليدوي على Windows أو الأجهزة الحقيقية.

## 8. حدود المراجعة الحالية

هذا المستند يسجل الجرد المعماري والمواضع الأعلى أولوية وخطة العمل التي يمكن تنفيذها تدريجيًا. لا يعلن تدقيقًا أمنيًا رسميًا، ولا يثبت صحة كل مسار وظيفي أو اكتمال قبول كل capability. حالة التنفيذ الفعلية تظل في سجل المتطلبات وتقارير القبول والـ CI المرتبطة بكل commit.
