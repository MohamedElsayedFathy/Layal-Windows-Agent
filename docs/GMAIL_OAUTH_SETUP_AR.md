# تكامل Gmail في ليال — قراءة الرسائل ومعاينات المرفقات

## النطاق والسلوك

التكامل مخصص لقراءة بريد Gmail عند طلب المستخدم داخل نافذة محلية في Layal. يستخدم Gmail API عبر HTTPS وصلاحية OAuth واحدة فقط:

`https://www.googleapis.com/auth/gmail.readonly`

هذه الصلاحية تسمح بقراءة الرسائل ومحتواها وبياناتها ومرفقاتها؛ وهي **Restricted scope** لدى Google وليست صلاحية بسيطة. راجع تصنيف النطاق ومتطلبات التحقق قبل توزيع التطبيق على مستخدمين آخرين.

- لا يحتوي التكامل على عمليات Gmail لإرسال الرسائل أو إنشاء المسودات أو حذف الرسائل أو تعديلها أو تغيير التصنيفات.
- لا توجد مزامنة خلفية أو مراقبة مستمرة لصندوق الوارد. تُجلب الرسائل فقط عند فتح نافذة Gmail أو ضغط «تحديث/بحث».
- يعرض التطبيق حتى 12 رسالة في كل تحميل من الواجهة، بينما لا تسمح الخدمة بطلب أكثر من 25 رسالة في الصفحة. البحث يستخدم صيغة Gmail المعتادة، ويُحد طول الاستعلام إلى 250 محرفًا. الاستعلام الأولي هو `newer_than:30d`.
- اختيار رسالة يجلب تفاصيلها ويعرض النص محليًا. لا يُشغّل HTML أو JavaScript أو الصور البعيدة أو النماذج أو iframes ولا يفتح روابط البريد تلقائيًا.
- محتوى البريد والمرفقات بيانات غير موثوقة؛ لا تتبع ليال أي تعليمات واردة داخلها ولا تنفذ ملفات أو ماكرو.

## المرفقات المدعومة وحدود المعاينة

تُعرض قائمة بالمرفقات المعروفة، مع حالة واضحة لكل مرفق. تتم معاينة الأنواع التالية فقط:

| النوع | الصيغ |
|---|---|
| نص UTF-8 | TXT, CSV, MD, JSON, XML, HTML, HTM |
| مستندات | PDF, DOCX, XLSX |
| صور للـ OCR المحلي | PNG, JPG, JPEG, BMP, TIF, TIFF |

حدود الحماية الحالية في الخدمة:

- حتى 20 مرفقًا لكل رسالة.
- 1 MiB كحد أقصى لكل مرفق. يعتمد قرار التنزيل أيضًا على الحجم الذي يبلّغ به Gmail، ثم يُفحص الحجم الفعلي بعد فك Base64؛ لا يُقبل المحتوى الأكبر من الحد حتى إذا كانت بيانات المرسل غير صحيحة.
- 3,000 محرف كحد أقصى لمعاينة المرفق الواحد و10,000 محرف إجمالًا لمعاينات مرفقات الرسالة.
- جسم الرسالة النصي: 15,000 محرف. استجابة الرسالة الكاملة من Gmail: 25 MiB كحد أقصى.
- الملفات النصية تُفك بترميز UTF-8 صارم؛ النص غير الصالح لا يُعرض كأنه صحيح.
- PDF وDOCX وXLSX والصور تُمرّر إلى محلل المستندات وOCR العربي/الإنجليزي المحليين. قد توجد أخطاء OCR ويجب مراجعة النتيجة.
- لا تُنزّل ليال المرفقات غير المدعومة أو التي تتجاوز الحد، ولا تفتح ملفات تنفيذية أو أرشيفات ZIP.
- عند استخراج المستند/الصورة، يُنشأ ملف مؤقت خاص باسم عشوائي في مجلد Temp، ثم يُحذف في مسار `finally`. لا يُنسخ الملف إلى مساحة عمل Layal، وتُصفّر مصفوفة بايتات المرفق بعد الاستخراج أو المعالجة.
- تلف مرفق أو تعذر تحليله لا يمنع عرض نص الرسالة وبقية المرفقات؛ تُعرض حالة فشل معاينة ذلك المرفق وحده. يُلغى الطلب إذا ألغى المستخدم العملية.

هذه حدود معاينة نصية وليست عارض ملفات كاملًا؛ لا يتم تنزيل نسخة قابلة للفتح أو حفظها للمستخدم.

## إعداد Google Cloud مرة واحدة

1. افتح [Google Cloud Console](https://console.cloud.google.com/) وأنشئ مشروعًا مخصصًا أو اختر مشروعًا تملكه.
2. من **APIs & Services → Library** فعّل **Gmail API**.
3. أكمل بيانات **Google Auth Platform / OAuth consent screen**: اسم التطبيق ووسيلة التواصل وسياسة الخصوصية والرابط/النطاقات المطلوبة عند الإتاحة العامة.
4. من **Data Access** أضف النطاق التالي وحده، ولا تضف `gmail.modify` أو `gmail.send` أو `https://mail.google.com/`:
   `https://www.googleapis.com/auth/gmail.readonly`
5. إذا كان نوع الجمهور **External** وحالة النشر **Testing**، أضف حساب Gmail التجريبي ضمن **Audience → Test users**.
6. من **Clients → Create client** اختر **Desktop app**، ثم انسخ **Client ID** المنتهي بـ `.apps.googleusercontent.com`.
7. لا تُدخل Client Secret أو API Key في ليال. تطبيقات Desktop عملاء OAuth عامة ولا يمكنها الاحتفاظ بسر عميل؛ يستخدم التدفق PKCE بدلًا منه.
8. افتح نافذة Gmail في ليال، أدخل Client ID العام، واقرأ إشعار الصلاحية ثم اختر «ربط Gmail». ستفتح ليال متصفح النظام وصفحة موافقة Google الرسمية.
9. اختر الحساب الصحيح وراجع أن الصلاحية المطلوبة هي قراءة Gmail فقط. بعد الرجوع إلى ليال اضغط «تحديث» لعرض الرسائل.

يستخدم التدفق عنوان loopback محليًا على `127.0.0.1` بمنفذ عشوائي، مع PKCE S256 وقيمة `state` عشوائية للتحقق من طلب العودة. يستمع التطبيق لطلب محلي واحد، ويتحقق من مصدر loopback وHTTP GET والمسار وقيمة state قبل استبدال رمز التفويض. مهلة تسجيل الدخول ثلاث دقائق ويمكن إلغاء العملية.

## التحقق والنشر لدى Google — شرط خارجي

`gmail.readonly` نطاق Restricted. استخدام حساب مطور أو Test user لا يعني أن التطبيق حصل على موافقة النشر العامة. قبل التوزيع على مستخدمين خارجيين، راجع مسار التحقق الحالي في Google وحدد ما إذا كان مشروعك يستفيد من استثناء الاستخدام الشخصي أو الاختبار أو الاستخدام الداخلي. التطبيقات العامة التي تتطلب Restricted scopes قد تحتاج تحقق النطاق، وقد يلزم تقييم أمني سنوي من طرف ثالث معتمد من Google عندما تصل بيانات النطاق المقيّد إلى خادم طرف ثالث أو تُدار من خلاله.

أثناء بقاء شاشة الموافقة في وضع Testing، قد تنتهي صلاحية Refresh Token بعد 7 أيام عند استخدام نطاق Gmail. لذلك لا تعتبر اختبار الاتصال لمدة أسبوع دليلًا على جاهزية النشر. حالة Google Cloud والتحقق القانوني/الأمني ليست شيئًا تستطيع اختبارات GitHub CI إكماله نيابة عن مالك التطبيق.

روابط Google الرسمية:

- [Gmail API — OAuth scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)
- [OAuth 2.0 for Desktop Apps](https://developers.google.com/identity/protocols/oauth2/native-app)
- [Restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)
- [OAuth 2.0 refresh token behavior](https://developers.google.com/identity/protocols/oauth2)
- [Google Workspace API User Data and Developer Policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)

## تخزين بيانات الاعتماد وإلغاء الوصول

- Client ID عام، يُحفظ في إعدادات Layal المحلية بعد التحقق من شكله. لا يعتبر سرًا.
- Refresh Token محفوظ في:
  `%LOCALAPPDATA%/Layal/secrets/gmail-refresh-token.dpapi`
- يحمي الملف Windows DPAPI ضمن حساب Windows الحالي؛ لا يُستخدم نطاق تشفير الجهاز المشترك.
- Access Token قصير العمر يبقى في ذاكرة الخدمة ويُجدد عند الحاجة. لا يُكتب في الإعدادات أو السجل.
- لا تسجل ليال الرسائل أو محتواها أو الرموز في سجل الأخطاء.
- زر **فصل محليًا** يحذف رمز Refresh Token من هذا الجهاز ويمسح Access Token الموجود في الذاكرة. هذا لا يسحب المنحة من Google. لإلغاء وصول التطبيق من Google أيضًا، افتح [إعدادات أمان حساب Google](https://myaccount.google.com/permissions) وأزل وصول Layal.
- نقل ملف DPAPI إلى حساب Windows آخر أو جهاز آخر لا ينقل التفويض؛ أعد الربط من الحساب المقصود.

## مشاركة محتوى البريد مع مزود الذكاء الاصطناعي

سياسة Google لبيانات Workspace تتطلب أن يكون استخدام بيانات Gmail لخدمة ظاهرة للمستخدم ومصرحًا بها، وأن يكون أي نقل للبيانات إلى طرف آخر واضحًا وموافقًا عليه. لا يجوز استخدام بيانات Gmail لتدريب نماذج AI عامة أو تحسينها خارج الاستخدام المخصص للمستخدم المسموح به في سياسة Google.

لذلك:

1. فتح الرسالة والبحث ومعاينة المرفقات تبقى محلية داخل Layal ولا تستدعي نموذج AI.
2. زر «إضافة إلى مسودة الشات» أو «تجهيز طلب تلخيص» يعرض تأكيدًا منفصلًا قبل نقل النص ومعاينات المرفقات إلى مربع مسودة الشات؛ هذا لا يستدعي AI ولا يرسل أي محتوى.
3. لا يغادر المحتوى الجهاز نحو المزود إلا عندما يراجع المستخدم المسودة ويضغط «إرسال» بنفسه.
4. عند الإرسال، ينتقل المحتوى إلى مزود AI المحدد في إعدادات Layal ويخضع لسياسة المعالجة والاحتفاظ الخاصة به. يجب على المستخدم مراجعة هذه السياسة والتأكد من توافق المزود واستخدامه الفعلي مع قيود بيانات Google قبل إرسال أي رسالة. لا تُرسل بريدًا إلى مزود لا تستطيع التحقق من أنه يلتزم بهذه القيود.
5. لا تبيع Layal بيانات Gmail أو تستخدمها للإعلانات أو لتدريب نماذج AI عامة داخل Layal. هذا لا يمثل ضمانًا لسياسات المزود الخارجي الذي يختاره المستخدم.

يمنع وضع **Incognito** فتح تكامل Gmail داخل Layal. ويظل الإرسال عبر Gmail نفسه غير متاح في كل الأوضاع.

## ما يثبته CI وما يتطلب حسابًا حقيقيًا

تختبر الاختبارات المحلية: PKCE وتحقق Client ID، تحويل HTML إلى نص دون تنفيذ محتواه، قائمة الرسائل عبر استجابات HTTP اختبارية، حدود النص والمعاينات، Allow-list للمرفقات، عدم طلب المرفقات غير المدعومة/الأكبر، معالجة ملف DOCX وصورة OCR محليًا، وحذف الملفات المؤقتة. لا تتصل هذه الاختبارات بحساب Gmail حقيقي ولا تتطلب إدخال رمز مستخدم.

القبول النهائي على Windows يتطلب OAuth Desktop Client حقيقيًا وحساب Gmail تجريبيًا، ومراجعة شاشة Google الفعلية، وتجربة رسائل ومرفقات حقيقية تالفة/سليمة، والتحقق من موافقة المستخدم قبل نقل محتوى البريد إلى مسودة الشات ثم إلى مزود AI. لا تُعتبر هذه الخطوات اليدوية مجتازة بمجرد نجاح CI.
