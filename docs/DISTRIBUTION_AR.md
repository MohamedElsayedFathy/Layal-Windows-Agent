# جاهزية حزمة التوزيع — Layal 0.5.2

هذه الصفحة تصف حزمة التوزيع التي يولّدها tools/Build-LayalDistribution.ps1 على Windows CI. نجاح التجميع أو إنشاء المثبّت لا يعني وحده أن الإصدار صالح للنشر العام.

## المخرجات

- Layal-Setup-<version>-win-x64.exe: مثبّت Inno Setup لكل مستخدم، يضيف اختصار Start Menu وخيار اختصار سطح المكتب، ويسجل التطبيق في Apps/Programs لإزالته.
- Layal-<version>-portable-win-x64.zip: مجلد تشغيل محمول مضغوط.
- sbom/Layal-<version>.cdx.json: قائمة مكونات CycloneDX للتبعيات المعروفة للمشروع.
- Layal-<version>-dependencies.txt: تقرير تبعيات .NET المباشرة والمتعدية.
- SHA256SUMS.txt: بصمات SHA-256 للملفات الموجودة في الحزمة باستثناء ملف البصمات نفسه.
- Layal-<version>-release-status.txt: يذكر صراحةً بوابات التوزيع التي لم يثبت إغلاقها.

## التثبيت والبيانات

التثبيت افتراضيًا في %LOCALAPPDATA%\Programs\Layal. أما بيانات المستخدم (الإعدادات، مفتاح المزود المشفر، المحادثات، المهام، الذاكرة والمهارات) فتبقى في %LOCALAPPDATA%\Layal خارج مجلد التطبيق. لا يعرّف المثبّت إجراءً لحذف مجلد البيانات عند الإزالة؛ يجب أن تبقى بيانات المستخدم محفوظة عند الترقية والتراجع وإزالة التطبيق.

الحزمة ذاتية التشغيل لـ Windows x64 وتتضمن ملفات Runtime الخاصة بـ .NET؛ لذلك لا يُفترض أن يثبت المستخدم .NET 10 منفصلًا. تظل تحديثات أمان .NET مسؤولية إعادة بناء الحزمة ونشر إصدار صيانة جديد.

## تحقق CI — دورة حياة المثبّت

اجتاز Windows CI التشغيل [39962310797](https://github.com/MohamedElsayedFathy/Layal-Windows-Agent/actions/runs/39962310797) على commit `e9a88503997df03b1e93e6dde44e9300108f68f6` دورة التثبيت الموسعة. الاختبار يعمل على مسار التثبيت الافتراضي `%LOCALAPPDATA%\\Programs\\Layal` بعد التأكد من عدم وجود تثبيت أو اختصار سابق، ويتحقق من:

- تثبيت إصدار الاختبار وتطابق `DisplayVersion` ووجود المُزيل في Apps/Programs.
- وجود اختصار Start Menu وتوجيهه إلى `Layal.exe` المثبّت.
- بقاء التطبيق قيد التشغيل في فحص بدء التشغيل بعد التثبيت والترقية والرجوع.
- ترقية الإصدار ثم الرجوع للإصدار الأقل مع بقاء محتوى ملف بيانات المستخدم التجريبي دون تغيير.
- بعد الإزالة: اختفاء ملفات التطبيق والمُزيل والاختصار وسجل Apps/Programs، مع بقاء محتوى ملف بيانات المستخدم كما هو.

تؤكد نتيجة CI نجاح هذه التأكيدات الآلية على عامل Windows نظيف؛ لكنها لا تحل محل القبول اليدوي على جهاز الهدف.

إصدار الرجوع المستخدم هو fixture اصطناعي `0.5.1` مبني من المصدر الحالي مع رقم إصدار أقل، وليس مُثبّتًا تاريخيًا حقيقيًا. لذلك يختبر هذا السيناريو ميكانيكا المُثبّت والتسجيل والإزالة وحفظ البيانات، لكنه لا يثبت التوافق مع ملفات ثنائية تاريخية أو ترحيل مخططات البيانات بين إصدارات قديمة.

## التحقق من SHA-256

بعد تنزيل الملفات، تحقق من البصمة المنشورة داخل SHA256SUMS.txt باستخدام PowerShell:

    Get-FileHash .\Layal-Setup-0.5.2-win-x64.exe -Algorithm SHA256

قارن قيمة Hash بالسطر المقابل داخل SHA256SUMS.txt. لا تستخدم ملف البصمات المرفق وحده لإثبات المصدر أو التوقيع؛ يجب الحصول عليه من قناة موثوقة.

## ما الذي ما زال يمنع إعلان الجاهزية النهائية؟

1. **التوقيع الرقمي:** حزم CI العادية غير موقعة بوضوح. إصدار tag من النمط `v*` يتطلب شهادة موثوقة وإجتياز تحقق Authenticode والطابع الزمني والبصمات؛ الإعداد الفعلي للشهادة عبر GitHub Actions Secrets ما زال مطلوبًا.
2. **التراخيص والإشعارات:** SBOM هو جرد آلي للمكونات وليس اعتمادًا قانونيًا. لم يظهر ملف يحدد رخصة المشروع نفسه ضمن ملفات المستودع التي راجعتها؛ يجب تحديدها وإضافة ملف الترخيص المناسب، ثم مراجعة رخص الحزم المباشرة والمتعدية والأصول المضمنة وتحديد الإشعارات المطلوبة قبل أي توزيع تجاري أو عام.
3. **القبول اليدوي:** يلزم تثبيت وتجربة على جهاز Windows نظيف، وفحص تشغيل التطبيق وإيقافه، وواجهة المستخدم ومنطقة الإشعارات، وتغيّر DPI والشاشات المتعددة، واللغة والثيم، والبيانات الحقيقية.
4. **سياسة الإصدار:** اختبارات CI لا تنشر إصدارًا عامًا تلقائيًا؛ يجب اتخاذ قرار صريح بشأن رقم الإصدار، وملاحظات الإصدار، وقناة التوزيع، وشهادة التوقيع.

حتى إغلاق هذه النقاط، تعامل مع المخرجات على أنها **حزمة تجريبية قابلة للاختبار** وليست إصدارًا عامًا معتمدًا.


## الأمان والتبعيات والتراخيص

- يفعّل Directory.Build.props تدقيق NuGet للشجرة الكاملة؛ ويصدر tools/audit_nuget.py تقريرًا آليًا قابلًا للرفع ويفشل المسار عند وجود استشارة ثغرة أو تعذّر التحقق من التقرير.
- يجمع فحص الأسرار بين نطاق الـ commits للتشغيل وفحص Git history صريح باستخدام Gitleaks على جميع المراجع والتاريخ المتاح في checkout، ويرفع تقرير SARIF. وتُطلب تحديثات أسبوعية للتبعيات وGitHub Actions عبر Dependabot.
- يحتوي مجلد licenses داخل المُثبّت والحزمة المحمولة على إشعارات الطرف الثالث ونصوص WTFPL وMIT وتوضيح صريح بأن رخصة Layal نفسها غير معلنة.
- جرد الرخص مبني على بيانات الحزم المنشورة ومقارنته بـ SBOM؛ وهو ليس اعتمادًا قانونيًا. رخصة المشروع وحقوق استخدام أصول الشخصية/الأيقونة ومراجعة التوافق القانوني ما زالت بوابات مفتوحة.


## المرحلة الرابعة — التوقيع الرقمي وسلامة الملفات

- في بناء CI العادي تظل الحزمة غير موقعة ما لم تتوفر شهادة Code Signing موثوقة؛ وتعرض حالة الإصدار ذلك صراحةً.
- أي tag يبدأ بـ `v` يدخل مسار إصدار صارمًا: لا تُرفع حزمة الإصدار ما لم تُوقّع `Layal.exe` والمُثبّت بشهادة Code Signing، مع timestamp من RFC 3161 باستخدام SHA-256، ثم ينجح التحقق بواسطة SignTool و`Get-AuthenticodeSignature`.
- لا تمرر خطوة التوقيع أسرار الشهادة إلى PR. عند الإصدار تستخدم أسرار GitHub Actions التالية فقط: `LAYAL_SIGNING_CERTIFICATE_BASE64` و`LAYAL_SIGNING_CERTIFICATE_PASSWORD` و`LAYAL_SIGNING_CERTIFICATE_THUMBPRINT`. لا تحفظ PFX أو كلمة مرورها داخل Git أو artifacts؛ ملف PFX المؤقت يُحذف بعد التوقيع.
- يُنشأ `SHA256SUMS.txt` بعد التوقيع، لذلك تطابق البصمات الملفات النهائية الموقعة. الفاحص المستقل يتحقق من كل بصمة ومن إدراج كل ملف في القائمة، ثم يفحص توقيع المُثبّت ونسخة `Layal.exe` داخل ZIP.
- يجب أن يشير tag الإصدار إلى commit موجود بالفعل ضمن تاريخ `main`. يجب كذلك تقييد صلاحية إنشاء tags من النمط `v*` يدويًا عبر قواعد حماية المستودع.

### إعداد الإصدار الموقّع

1. احصل على شهادة Windows Code Signing موثوقة وصالحة، تحمل Enhanced Key Usage الخاص بالتوقيع البرمجي، مع المفتاح الخاص داخل PFX.
2. أضف الأسرار الثلاثة المذكورة أعلاه في GitHub Repository Settings → Secrets and variables → Actions. قيمة Base64 تُعامل بنفس حساسية ملف PFX؛ فهي ليست تشفيرًا للمفتاح.
3. قيد إنشاء tags من النمط `v*` على مسؤولي الإصدار عبر ruleset أو tag protection في إعدادات GitHub. لا تُنشئ tag إصدار نهائي قبل ضبط الأسرار وسياسة صلاحياته.
4. بعد دمج التغييرات إلى `main` وإنشاء tag مثل `v0.5.2`، يجب أن ينجح تشغيل Windows CI في التوقيع والتحقق والبصمات؛ أي غياب للأسرار أو فشل في التوقيع/الختم الزمني يوقف نشر artifacts لهذا tag.

لم تُقدَّم شهادة توقيع فعلية في هذا العمل، ولا يُدّعى أن artifacts مرحلة التطوير قد وُقّعت. مسار CI العادي يبقى غير موقع بوضوح؛ ومسار tag يرفض إنتاج artifact إصدار إذا لم تتوفر شهادة موثوقة والتحقق الكامل.
