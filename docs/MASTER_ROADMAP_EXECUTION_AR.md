**تاريخ التحديث:** 13 نوفمبر 2026  
**المستودع:** `MohamedElsayedFathy/Layal-Windows-Agent`  
**الفرع الذي تم تحديثه:** `main` — دون إنشاء فرع جديد  
**خط الأساس:** `4df2a067c4c6df161d140e2f06d252745c1f8d3b`

**الحالة العامة:** تطوير داخلي؛ قرار التوزيع العام ما زال **NO-GO** حتى إغلاق بوابات القبول اليدوي والتوقيع والحقوق والتراخيص.

## 1. ملخص الحالة الحالية

وصل `main` إلى commit `4df2a067c4c6df161d140e2f06d252745c1f8d3b` بعد دمج PR #166. المشروع يحتوي الآن على نواة محلية رمزية محدودة، وإدارة ذاكرة وملفات، ومجموعة أدوات للمتصفح وWindows وواجهات API، وخدمات صوت وكاميرات ومستندات. لكن وجود الأداة في المصدر لا يعني بالضرورة أن النواة المحلية النشطة تستطيع استدعاءها؛ كما أن نجاح CI لا يساوي قبولًا يدويًا على جهاز Windows حقيقي.

أهم نتيجة تنظيمية: اكتملت حزمة استخراج مسؤوليات تنفيذ الأدوات من `AgentToolExecutor` عبر PRs #162 إلى #166. والخطوة المعمارية التالية هي تفكيك `BrowserAutomationService`، بدءًا بخدمة قراءة الصفحات، ثم فصل أفعال المتصفح وإدارة جلسة Edge.

**نتيجة آخر بوابة CI مرتبطة مباشرةً بالتغيير الأخير:** نجحت الفحوص الأربعة على رأس PR #166 `dea41bcff73898bce28e2d0d6ba26100ec725d6a`: Windows build، وFull Windows acceptance الآلي، وتدقيق NuGet والتراخيص، وفحص الأسرار. دُمج PR #166 في `main` بطريقة Squash. هذا لا يغلق اختبارات سطح المكتب الفعلية أو الأجهزة الحقيقية.

## 2. معاني الحالة — لا تخلط بين التنفيذ والقبول

| الحالة | معناها |
|---|---|
| **تم** | التنفيذ المطلوب لهذه الحزمة موجود في `main`، واجتاز فحوص CI المحددة لها عند ذكر ذلك. لا تعني تلقائيًا قبول الجهاز الحقيقي. |
| **تم في المصدر — قبول عملي معلق** | الكود موجود، لكن يلزم اختبار يدوي على Windows أو مع حساب/موقع/جهاز حقيقي قبل إعلان اكتمال الوظيفة. |
| **جزئي / محدود** | جزء من الوظيفة موجود، لكن النطاق الحالي أضيق من الهدف النهائي أو لا يعمل عبر النواة المحلية النشطة كلها. |
| **غير منفذ** | لا توجد قدرة مكتملة قابلة للاستخدام في النطاق المقصود. |
| **قرار مطلوب** | توجد رؤى أو تصاميم متعارضة ويجب اعتماد قرار معماري قبل كتابة التنفيذ. |

## 7. ترتيب التنفيذ القادم

### الحزمة التالية — تفكيك BrowserAutomationService

**الحالة:** لم تُبدأ بعد.  
**المبرر:** بعد PRs #164–#166 أصبحت سياسة المتصفح ونقل CDP وتنفيذ البحث/المتصفح منفصلة؛ بقيت خدمة المتصفح نفسها تجمع دورة حياة Edge وقراءة الصفحة وتنفيذ الأفعال. حجم الملف في خط الأساس الحالي يقارب 1,108 أسطر.

1. استخراج `BrowserPageReadService` لقراءة هوية التبويب والصفحات ولقطات المحتوى والتحقق من ثبات التبويب قبل/بعد القراءة.
2. استخراج `BrowserActionService` لمعاينة العناصر والنقر وإدخال النص ورفع الملفات، مع إبقاء إعادة التحقق وبصمات العنصر وموافقات المستخدم.
3. فصل `EdgeSession` أو مكوّن مماثل لإدارة بدء Edge والجلسة الحالية والإغلاق والاستعادة والإلغاء دون سباق مع CDP.
4. الحفاظ على `BrowserAutomationPolicy` و`BrowserCdpTransport` كحدود مستقلة، وعدم تكرار قواعد URL/DNS/redirect في الخدمات الجديدة.
5. إضافة/تحديث اختبارات الانحدار لتبدل التبويب، redirect وDNS، selectors، upload lease/hash، same-origin downloads، cancellation وshutdown.
6. فتح PR مستقل، وتشغيل Windows build/tests/full acceptance/security checks، ثم مراجعة diff قبل أي دمج.

## 8. قواعد التنفيذ والتحديث

1. يُعامل هذا الملف كخريطة التطوير الرئيسية الحية وسجل التنفيذ؛ مصفوفة المراحل في القسم 2 هي مرجع الحالة الحالي، والملحق (أ) يحفظ النطاق التفصيلي الأصلي كاملًا.
2. لا تكتب **تم** على وظيفة إلا إذا كان نطاقها واضحًا وموجودًا في `main`. سجّل CI والقبول العملي كلًا على حدة.
3. لا تعتبر وجود Tool Definition أو Service دليلًا على أن النواة المحلية النشطة تستطيع استدعاءها؛ تحقق من مسار `NativeLanguageParser` و`NativeAgentOrchestrator` والواجهة.
4. لا تعتبر نجاح Windows CI قبولًا يدويًا على جهاز المستخدم، ولا تعتبر اختبارًا اصطناعيًا للكاميرا/المتصفح/Google بديلًا عن الحساب أو الجهاز الحقيقي.
5. لا تضف صلاحيات جديدة أثناء refactoring ميكانيكي، ولا تضعف الموافقات أو حدود مساحة العمل أو التحقق من الوجهة أو حماية الأسرار.

**1.2 مبادئ غير قابلة للتفاوض**

> • Local First: وظائف الذكاء الأساسية تعتمد على نموذج محلي.
>
> • No Mandatory AI API: لا يُشترط مفتاح AI API للمحادثة أو التخطيط أو المهام المحلية الأساسية.
>
> • No Silent Cloud Fallback: لا تنتقل ليال إلى مزود خارجي عند فشل المحلي دون موافقة مسبقة وسياسة واضحة.
>
> • Privacy by Design: البيانات تظل محلية افتراضيًا، ومشاركة البيانات الخارجية معلنة ومحددة.
>
> • User Control: المستخدم يحدد المجالات والمصادر والموارد والصلاحيات ومستوى الاستقلال.
>
> • Safe Execution: الأكواد والمهارات والعمليات الحساسة تعمل في بيئات وحدود مناسبة.
>
> • Verifiable Results: لا تعلن ليال نجاح عملية إلا بعد التحقق من أثرها.
>
> • Reversible Changes: النسخ الاحتياطي والإصدارات والرجوع جزء من التصميم.
>
> • Extensibility: إضافة مهارات وموصلات جديدة دون إعادة بناء عقل ليال.
>
> • Continuous Learning: التعلم المستمر لا يعني تغيير النموذج الأساسي تلقائيًا أو اعتبار كل معلومة صحيحة.

**1.3 تعريف الاستقلال وحدوده**

الاستقلال المقصود هو الاستقلال عن مزود الذكاء الاصطناعي الخارجي، وليس الاستقلال عن كل خدمة أو بنية تشغيل. GitHub وGmail وREST والبحث على الإنترنت تظل خدمات مستقلة تحتاج اتصالًا وصلاحياتها الخاصة. تشغيل نموذج محلي لا يلغي الحاجة إلى الاتصال بخدمة GitHub عندما يطلب المستخدم تعديل مستودع بعيد.

العمل Offline يعني أن الوظائف التي لا تحتاج موردًا خارجيًا تستمر دون إنترنت بعد اكتمال التنزيل والتجهيز. تنزيل نموذج أو الوصول إلى مستودع GitHub أو البحث الحي أو إرسال API خارجي بطبيعته يحتاج اتصالًا.

> • إضافة معالجة إطارات محلية على دفعات بدل بث الفيديو إلى Cloud.

**7.1 تعريف اكتمال الحزمة (Definition of Done)**

1\. نطاق الحزمة واضح ولا يتوسع دون موافقة.

2\. التغيير في Branch مستقل ولا يكتب على main مباشرة.

3\. التصميم متوافق مع نموذج الاستقلال المحلي وقواعد الأمان.

4\. الاختبارات تغطي النجاح والفشل والرفض والإلغاء والمهلة.

5\. نجاح Windows build والاختبارات المرتبطة بالتغيير.

6\. مراجعة diff والاعتماديات والأسرار والتراخيص ذات الصلة.

7\. تحديث سجل المتطلبات وBUGLOG وtraceability عند الحاجة.

8\. إرفاق أدلة القبول العملي المطلوبة أو ترك الحالة Pending بوضوح.

9\. مراجعة ودمج PR بعد موافقة المستخدم، ثم التحقق من وصوله إلى main.

10\. عدم بدء الحزمة التالية قبل إغلاق الموانع أو توثيق اعتمادياتها.
