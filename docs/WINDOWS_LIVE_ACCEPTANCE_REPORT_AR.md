## 2. قواعد تسجيل النتيجة

استخدم حالة واحدة لكل بند:

- **PASS**: أُجري الاختبار على الجهاز المحدد، وسُجلت النتيجة الفعلية والدليل.
- **FAIL**: أُجري الاختبار ولم يتحقق المتوقع؛ احتفظ بالسجل والصورة ولا تتجاوز الإخفاق.
- **NOT TESTED**: لم يُشغّل الاختبار.
- **BLOCKED**: تعذر الاختبار بسبب متطلب مفقود؛ اذكر السبب. لا تعامل BLOCKED أو NOT TESTED كنجاح.

يجب أن يحتوي كل سجل على المعرّف والحالة والنتيجة المرصودة ومسار الدليل وإصدار البناء. أعد الاختبار بعد الإصلاح على الـ commit المرشح نفسه.

## 4. أوامر التشخيص المتاحة

### تشغيل حزمة تشخيص موحّدة على جهاز Windows فعلي

يوفّر الملف tools/Start-LayalLiveAcceptance.ps1 مشغّلًا واحدًا للاختبارات التفاعلية الموجودة: تمرير النقرات الأصلي، والسحب، والتنقل بلوحة المفاتيح، ومعاينة GLB المتحركة، ورصد الشاشة وDPI. يجمع سجلاتها في مجلد جلسة واحد مع إصدار Windows، وعدد الشاشات وحدودها، وإصدار الملف التنفيذي وبصمة SHA-256، والـ commit الذي بُني منه التطبيق.

**لا تشغّل هذا الأمر في GitHub Actions أو جلسة غير تفاعلية.** أجره على جهاز Windows المستهدف، من checkout كامل على نفس الـ commit الذي بُني منه ملف Layal.exe. سيحرّك الاختبار بعض النوافذ والمؤشر، لذا اترك سطح المكتب للاختبار وأغلق التطبيقات المهمة أولًا.

\`\`\`powershell
git checkout <EXACT-TESTED-COMMIT-SHA>
dotnet build Layal.sln --configuration Release
$testedCommitSha = (git rev-parse HEAD).Trim()
$acceptanceArgs = @{
  LayalExePath = ".\src\Layal.Desktop\bin\Release\net10.0-windows10.0.19041.0\Layal.exe"
  DeviceId = "lab-device-01"
  TestedCommitSha = $testedCommitSha
  ArtifactReference = "https://github.com/MohamedElsayedFathy/Layal-Windows-Agent/actions/runs/<RUN-ID>"
}
& ".\tools\Start-LayalLiveAcceptance.ps1" @acceptanceArgs
\`\`\`

استبدل <EXACT-TESTED-COMMIT-SHA> و<RUN-ID> بالقيم الفعلية للحزمة المختبرة. يجب أن يكون ArtifactReference رابط HTTPS لتشغيل البناء أو الـ artifact نفسه، وأن يطابق TestedCommitSha قيمة HEAD. استخدم معرّف جهاز غير شخصي. ولإلزام اختبار انتقال فعلي بين شاشتين مضبوطتين على مقاسي DPI مختلفين، أضف المفتاح -RequireMixedDpiTransition؛ عندئذ يفشل الاختبار إذا لم يرصد الانتقال المطلوب.

ينشئ المشغّل live-acceptance-session.json وmanual-checklist.csv وسجلات فرعية لكل اختبار داخل artifacts/windows-live-acceptance/. سيظل قرار الجلسة NO-GO وبوابات القبول اليدوي PENDING حتى بعد نجاح الاختبارات الآلية؛ لا يختبر المشغّل وحده Narrator/NVDA أو High Contrast أو القبول البصري البشري، ولا يعدّ نجاح CI قبولًا حيًا. أكمل المراجعة اليدوية وأدلّتها قبل تحديث docs/RELEASE_GATE_EVIDENCE.json.

### رصد الشاشة وDPI

    pwsh -NoProfile -ExecutionPolicy Bypass -File .\tools\Test-LayalDisplayDpi.ps1 -LayalExePath ".\src\Layal.Desktop\bin\Release\net10.0-windows\Layal.exe" -ObserveSeconds 90 -RequireMultipleMonitors -RequireMonitorTransition -RequireDpiTransition -LogDirectory "artifacts/windows-live-acceptance/display-dpi"

أثناء الرصد، اسحب الشخصية فعليًا بين شاشتين مضبوطتين على مقياسين مختلفين. افحص `display-dpi-summary.json` و`display-dpi-samples.csv`. يجب أن تكون `TopologyDpiGateStatus=passed` و`TopologyDpiTransitionsObserved=true` لاعتماد انتقال الشاشة/DPI فقط. يجب أن تظل `ManualVisualAcceptanceStatus=pending` حتى مراجعة الصور البشرية وتسجيلها.

### تمرير النقرات

    pwsh -NoProfile -ExecutionPolicy Bypass -File .\tools\Test-LayalClickThrough.ps1 -LayalExePath ".\src\Layal.Desktop\bin\Release\net10.0-windows\Layal.exe"

اتبع تعليمات نافذة الاختبار وتحقق من وصول النقرة فعليًا إلى الهدف الخلفي في الفراغ الشفاف، وعدم وصولها عند النقر على الشخصية المرئية. احفظ ملف CSV، ثم أغلق نافذة الاختبار يدويًا.

### تحقق إضافي من التوزيع

إذا توفرت نسخة `VERIFY-LAYAL.ps1` في الفرع المرشح، شغّلها واحفظ المخرجات الكاملة؛ لا تستبدل ذلك بمقارنة اسم الملف وحده. تحقق من بصمة SHA-256 من قناة موثوقة، لأن ملف البصمات المرفق وحده لا يثبت أصالة الناشر.

## 5. شروط قرار القبول

لا يُعلن القبول النهائي قبل أن:

1. تكون جميع بنود التشغيل الأساسية وTray والنقر والسحب واللغة والثيم وحفظ الإعدادات والخصوصية **PASS** مع أدلة.
2. يُختبر كل من تغيير DPI وتعدد الشاشات فعليًا إذا كانا ضمن أجهزة/متطلبات الإصدار المستهدفة؛ أي متطلب غير متاح يُذكر صراحةً ولا يُحوّل إلى PASS.
3. لا توجد إخفاقات مفتوحة في حفظ البيانات أو الموافقات الأمنية أو سلامة دورة الحياة. تُسجّل حدود الرجوع بمثبت تاريخي حقيقي بشكل مستقل عن fixture الاصطناعي المستخدم في CI.
4. ينجح Windows CI لنفس commit وتُفحص تقارير الاختبار والحزمة.
5. يُتخذ قرار إصدار مستقل؛ نجاح القبول اليدوي لا يغلق بوابة التوقيع الرقمي أو مراجعة تراخيص المشروع وأصول الشخصية وSBOM. حزمة غير موقعة أو بلا ترخيص مشروع واضح ليست إصدارًا عامًا معتمدًا.
